# 意圖與範圍分類框架

這個技能是給 tech lead 用的判斷輔助，不是用來取代你的判斷。輸出永遠是**草案**，需要你確認才算數。

## 分類框架（每次都要完整跑過，不要跳步）

針對輸入的內容（可以是 `ingest-doc` 產出的事實清單，也可以是使用者直接貼的文件），依序回答：

1. **目標**：這份東西真正想達成的結果是什麼？用一句話講清楚「為什麼要做這件事」，不是「要做什麼功能」。
2. **明說的範圍**：文件/討論裡直接寫出來、明確要做的項目。
3. **隱含的非目標**：雖然沒明講，但從上下文可以合理推斷「這次不做」的項目。每一項都要附上推斷依據，不要憑空列。
4. **待釐清**：模稜兩可、多方說法不一致、或缺少關鍵資訊而無法歸類到「範圍內」或「範圍外」的項目。**這一類永遠不能是空的就直接跳過不寫** —— 如果暫時想不到待釐清項目，明確寫「目前沒有發現待釐清項目」，而不是省略這個段落。
5. **POC / 探索候選**：任何依賴不確定技術可行性、需要先驗證才能估工的項目，獨立列出，不要混進「範圍內」。

## 硬性規則

- **禁止把「待釐清」偷偷歸類成「範圍內」或「範圍外」來讓輸出看起來更乾淨**。不確定就是不確定，寧可清單長一點也不要幫忙做決定。
- 每一項分類都盡量附來源引用（如果輸入是 `ingest-doc` 的事實清單，直接沿用其編號）。
- 如果輸入內容本身就有衝突（例如兩份文件對範圍的說法不同），優先把這個衝突放進「待釐清」，並在旁邊註明是哪些來源衝突，而不是自己選一個當作正確答案。

## 輸出格式

```markdown
## 目標
一句話說明

## 範圍內
- 項目（來源）

## 範圍外（推斷的非目標）
- 項目 — 推斷依據

## 待釐清
- 項目 — 為什麼無法歸類

## POC / 探索候選
- 項目 — 需要驗證什麼
```

## 完成後

主動詢問使用者：「待釐清的項目要不要我幫忙整理成問題清單，方便你回去跟 PM/架構師確認？」不要自己去猜答案填上。如果使用者確認了這份分類要正式記錄下來，接著建議使用 `reconcile-state` 技能寫入專案狀態庫。
