# 意圖與範圍分類框架

這個技能是給 tech lead 用的判斷輔助，不是用來取代你的判斷。輸出永遠是**草案**，需要你確認才算數。

## 第 -1 步：判斷屬於哪個 Feature（在做任何分類之前）

先讀 `project-state/features/INDEX.md`（進行中功能）跟 `project-state/archive/INDEX.md`（已封存功能），判斷這份新資訊屬於：

1. **既有的進行中 feature** — 直接沿用該 feature 的 slug，後續分類結果會寫進 `features/<slug>/`
2. **已封存的 feature，且有明確需要處理的決策/需求變動** — 提醒使用者「這個功能之前已經封存，這次是否要重新啟動？」，如果使用者同意，`reconcile-state` 那一步會負責把資料夾搬回 `features/` 並記錄重新啟動原因；`scope-doc` 這一步只需要標明「這是重新啟動的既有 feature」，不用自己動手搬檔案
3. **已封存的 feature，但只是輕描淡寫提及、沒有實質新決策要處理** — 不觸發重新啟動，直接回覆確認即可，不需要往下走完整分類流程
4. **全新的 feature** — 提議一個簡短的 slug（例如 `031-batch-export`），標明這是新功能
5. **跨功能、不屬於單一 feature 的內容**（例如全域技術規範）— 標明「這屬於 global，不屬於單一 feature」

**判斷依據**：主題、關鍵字、涉及的模組跟既有 feature 是否相符。如果比對不出來、或有兩個以上候選都很像，不要自己選一個，明確問使用者這屬於哪個 feature。

## 第 0 步：情報完整度檢查（在分類之前先做）

在套用下面的分類框架之前，先對照這份標準檢查清單，逐項確認手上的資料**有沒有涵蓋到**：

- 使用者/情境：誰會用這個功能、在什麼情境下用
- 資料範圍：涉及哪些資料、資料量級
- 效能與規模要求
- 例外/邊界情況處理
- 相容性或既有系統的相依關係
- 安全與權限要求
- 驗收標準（怎樣算做完）

任何一項完全沒被來源資料提到，先不要急著發問回去——**先確認是不是還有其他尚未消化的來源可能涵蓋這塊**，提醒使用者要不要先用 `ingest-doc` 補看那份來源。如果確認沒有其他來源了，才把這個維度正式列為「資訊缺口」，進到下面的分類框架。

**這一步的目的是把「資訊缺口」跟後面的「待釐清」明確分開**：待釐清是「有講但講不清楚，該去問細節」；資訊缺口是「完全沒資料，該先確認有沒有別的來源，沒有才發問」。不要把這兩種混在一起處理。

## 分類框架（每次都要完整跑過，不要跳步）

針對輸入的內容（可以是 `ingest-doc` 產出的事實清單，也可以是使用者直接貼的文件），依序回答：

1. **目標**：這份東西真正想達成的結果是什麼？用一句話講清楚「為什麼要做這件事」，不是「要做什麼功能」。
2. **明說的範圍**：文件/討論裡直接寫出來、明確要做的項目。
3. **隱含的非目標**：雖然沒明講，但從上下文可以合理推斷「這次不做」的項目。每一項都要附上推斷依據，不要憑空列。
4. **待釐清（表述模糊/衝突）**：來源有提到、但講得模稜兩可，或多方說法不一致的項目。**這一類永遠不能是空的就直接跳過不寫** —— 如果暫時想不到，明確寫「目前沒有發現待釐清項目」。每一項都要附上**提議預設值**：「若未獲回覆，建議先假設：X」。
5. **資訊缺口**：來自第 0 步檢查、確認沒有其他來源可查的項目。跟「待釐清」分開列。同樣不能省略這個段落，同樣附上**提議預設值**，想不出合理預設就老實寫「無法提出合理預設，必須發問」。
6. **POC / 探索候選**：任何依賴不確定技術可行性、需要先驗證才能估工的項目，獨立列出，不要混進「範圍內」。

## 硬性規則

- **禁止把「待釐清」或「資訊缺口」偷偷歸類成「範圍內」或「範圍外」來讓輸出看起來更乾淨**。
- **禁止用「業界慣例通常是這樣」這類推測去悄悄填補資訊缺口**。
- **提議預設值不等於採用預設值**——在使用者明確確認之前，狀態仍然是待釐清/資訊缺口。
- **不要自己判斷 feature 歸屬並直接寫入，第 -1 步的判斷一樣是草案，要讓使用者確認**，尤其是「是否重新啟動已封存功能」這種決定影響較大，一定要明確問過。
- 每一項分類都盡量附來源引用。
- 如果輸入內容本身就有衝突，優先把這個衝突放進「待釐清」，並註明是哪些來源衝突。

## 輸出格式

```markdown
## Feature 歸屬
判斷結果：既有 feature（<slug>）／重新啟動已封存 feature（<slug>）／新 feature（建議 slug：<slug>）／global
判斷依據：...

## 情報完整度檢查
- 維度：涵蓋 / 資訊缺口（如為缺口，註明是否已確認沒有其他來源可查）

## 目標
一句話說明

## 範圍內
- 項目（來源）

## 範圍外（推斷的非目標）
- 項目 — 推斷依據

## 待釐清（表述模糊/衝突）
- 項目 — 為什麼無法歸類 — 提議預設：X

## 資訊缺口
- 項目 — 已確認查過哪些來源都沒提到 — 提議預設：X（或「無法提出合理預設，必須發問」）

## POC / 探索候選
- 項目 — 需要驗證什麼
```

## 完成後

主動詢問使用者：「待釐清跟資訊缺口的項目，要不要我幫忙整理成問題清單？」如果使用者確認了 feature 歸屬跟分類要正式記錄下來，接著建議使用 `reconcile-state` 技能寫入專案狀態庫（如果是重新啟動已封存功能，`reconcile-state` 那一步會負責搬移資料夾）。
