# 意圖與範圍分類框架

這個技能是給 tech lead 用的判斷輔助，不是用來取代你的判斷。輸出永遠是**草案**，需要你確認才算數。

## 第 0 步：情報完整度檢查（在分類之前先做）

在套用下面的分類框架之前，先對照這份標準檢查清單，逐項確認手上的資料**有沒有涵蓋到**：

- 使用者/情境：誰會用這個功能、在什麼情境下用
- 資料範圍：涉及哪些資料、資料量級
- 效能與規模要求
- 例外/邊界情況處理
- 相容性或既有系統的相依關係
- 安全與權限要求
- 驗收標準（怎樣算做完）

任何一項完全沒被來源資料提到，先不要急著發問回去——**先確認是不是還有其他尚未消化的來源可能涵蓋這塊**（例如「這份 PRD 沒提效能要求，但架構師的 Slack thread 裡會不會提過？」），提醒使用者要不要先用 `ingest-doc` 補看那份來源。如果確認沒有其他來源了，才把這個維度正式列為「資訊缺口」，進到下面的分類框架。

**這一步的目的是把「資訊缺口」跟後面的「待釐清」明確分開**，因為兩者需要的下一步動作不同：待釐清是「有講但講不清楚，該去問細節」；資訊缺口是「完全沒資料，該先確認有沒有別的來源，沒有才發問」。不要把這兩種混在一起處理。

## 分類框架（每次都要完整跑過，不要跳步）

針對輸入的內容（可以是 `ingest-doc` 產出的事實清單，也可以是使用者直接貼的文件），依序回答：

1. **目標**：這份東西真正想達成的結果是什麼？用一句話講清楚「為什麼要做這件事」，不是「要做什麼功能」。
2. **明說的範圍**：文件/討論裡直接寫出來、明確要做的項目。
3. **隱含的非目標**：雖然沒明講，但從上下文可以合理推斷「這次不做」的項目。每一項都要附上推斷依據，不要憑空列。
4. **待釐清（表述模糊/衝突）**：來源有提到、但講得模稜兩可，或多方說法不一致的項目。**這一類永遠不能是空的就直接跳過不寫** —— 如果暫時想不到，明確寫「目前沒有發現待釐清項目」，而不是省略這個段落。
5. **資訊缺口**：來自第 0 步檢查、確認沒有其他來源可查的項目。跟「待釐清」分開列，因為這不是「講不清楚」，是「完全沒講」。同樣不能省略這個段落，沒有的話明確寫「目前沒有發現資訊缺口」。
6. **POC / 探索候選**：任何依賴不確定技術可行性、需要先驗證才能估工的項目，獨立列出，不要混進「範圍內」。

## 硬性規則

- **禁止把「待釐清」或「資訊缺口」偷偷歸類成「範圍內」或「範圍外」來讓輸出看起來更乾淨**。不確定就是不確定，寧可清單長一點也不要幫忙做決定。
- **禁止用「業界慣例通常是這樣」「一般來說都會」這類推測去悄悄填補資訊缺口**。資訊缺口就是缺口，要老實列出來，不能用常見假設偷渡成既定範圍。
- 每一項分類都盡量附來源引用（如果輸入是 `ingest-doc` 的事實清單，直接沿用其編號）。
- 如果輸入內容本身就有衝突（例如兩份文件對範圍的說法不同），優先把這個衝突放進「待釐清」，並在旁邊註明是哪些來源衝突，而不是自己選一個當作正確答案。

## 輸出格式

```markdown
## 情報完整度檢查
- 維度：涵蓋 / 資訊缺口（如為缺口，註明是否已確認沒有其他來源可查）

## 目標
一句話說明

## 範圍內
- 項目（來源）

## 範圍外（推斷的非目標）
- 項目 — 推斷依據

## 待釐清（表述模糊/衝突）
- 項目 — 為什麼無法歸類

## 資訊缺口
- 項目 — 已確認查過哪些來源都沒提到

## POC / 探索候選
- 項目 — 需要驗證什麼
```

## 完成後

主動詢問使用者：「待釐清跟資訊缺口的項目，要不要我幫忙整理成問題清單，方便你回去跟 PM/架構師確認？」不要自己去猜答案填上。如果使用者確認了這份分類要正式記錄下來，接著建議使用 `reconcile-state` 技能寫入專案狀態庫。
