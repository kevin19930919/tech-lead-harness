# 把待釐清項目轉成問回上游的訊息

## 步驟

1. 確認要處理哪個/哪些 feature（可以是單一 feature，也可以是「所有進行中 feature」——先問清楚使用者要哪種範圍，不要自己決定）。

2. 針對每個 feature，各自掃描 `project-state/features/<slug>/decisions.md`、`backlog.md`、`risks.md`，找出所有 `[待釐清]`、資訊缺口與 `[有衝突]` 的項目。如果同時處理多個 feature，**分開整理、分開輸出，不要把不同 feature 的問題混在同一份清單裡**——不同 feature 很可能對應不同的 PM/架構師，混在一起對收件人來說會很奇怪。

3. 把每一項改寫成**具體、可回答**的問題，而不是把原本模糊的描述直接複製過去當問題。

4. **每個問題都要附上預設答案**（如果 `scope-doc` 階段已經附過「提議預設值」，直接沿用，不要重新想一次），格式類似：「若沒空回覆，我會照 [預設方案] 往下走」。

5. `[有衝突]` 的項目，兩邊來源的說法都要列出來，明確請對方裁定，**不要暗示哪一邊比較可能是對的**，也不附預設答案。

6. 每個 feature 的訊息結尾都要有明確的一段：**「範圍外（除非你特別提出）」**，把該 feature 目前判斷為範圍外、但還沒正式跟對方確認過的項目列出來。

7. 每個問題附上簡短背景，讓對方不用回頭翻文件也能直接回答。
8. 依照「會不會卡住接下來的開發」排序。
9. 如果環境支援訊息草擬工具，用它產生 Slack 或 email 版本；不支援的話直接輸出 Markdown 格式的問題清單。

## 硬性規則

- 不要自己猜答案、幫忙填上「應該是這樣吧」——附預設答案是**明確提議**，跟悄悄猜答案不一樣
- 衝突類的問題不附預設答案，一定要對方明確裁定
- 不同 feature 的問題不能合併成一份清單
- 每個問題都要可以被單獨回答
- 範圍外聲明段落不能省略

## 輸出格式

```markdown
## Feature：<slug>

### 待確認事項（依急迫程度排序）
1. **[問題]**
   背景：為什麼會有這個疑問，來源是什麼
   預設：若沒空回覆，我會照 [預設方案] 往下走

### 範圍外（除非你特別提出）
- 項目 — 判斷依據
```

如果處理多個 feature，重複上面的區塊，每個 feature 各自一份。

## 完成後

提醒使用者：「這些問題送出去之後，對方的回覆記得用 `ingest-doc` 重新消化一次，並註明是回覆哪一則問題、對應哪個 feature」——這樣回覆才會正確地成為下一輪迴圈的新資訊。
