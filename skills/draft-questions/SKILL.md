# 把待釐清項目轉成問回上游的訊息

## 步驟

1. 掃描 `project-state/decisions.md`、`backlog.md`、`risks.md`，找出所有 `[待釐清]`、資訊缺口與 `[有衝突]` 的項目。如果這些項目在 `scope-doc` 階段已經附過「提議預設值」，直接沿用，不要重新想一次。

2. 把每一項改寫成**具體、可回答**的問題，而不是把原本模糊的描述直接複製過去當問題。

   不好的問法：「這個功能的範圍是什麼？」（太空泛，對方也不知道從何答起）
   好的問法：「範圍是否包含批次匯出？如果包含，CSV 和 Excel 兩種格式都要在第一版做，還是可以先做一種？」

3. **每個問題都要附上預設答案**，格式類似：「若沒空回覆，我會照 [預設方案] 往下走」。這樣做兩件事：降低對方回覆的門檻（他只要確認或反對，不用從零想答案），同時保護你自己——之後如果有爭議，能證明當初有問過、也講清楚了沒回覆會怎麼處理。

4. `[有衝突]` 的項目，兩邊來源的說法都要列出來，明確請對方裁定，**不要暗示哪一邊比較可能是對的**，也不要在這種情況下附預設答案——衝突需要對方明確裁定，不適合用「不回覆就照預設走」的方式處理。

5. 訊息結尾要有明確的一段：**「範圍外（除非你特別提出）」**，把目前判斷為範圍外、但還沒正式跟對方確認過的項目列出來。這是你之後拒絕 scope creep 的依據——如果對方當時沒有反對，之後要加範圍就是新的討論，不是「你本來就該做」。

6. 每個問題附上簡短背景（為什麼會產生這個疑問、來源是什麼），讓對方不用回頭翻文件也能直接回答。
7. 依照「會不會卡住接下來的開發」排序，最急迫的放最前面，不要照檔案裡原本的順序照抄。
8. 如果環境支援訊息草擬工具，用它產生 Slack 或 email 版本；不支援的話直接輸出 Markdown 格式的問題清單。

## 硬性規則

- 不要自己猜答案、幫忙填上「應該是這樣吧」——這些項目會被列進這裡，就是因為你不該猜。附預設答案是**明確提議**，跟悄悄猜答案不一樣：預設答案要寫在訊息裡讓對方看到、可以反對，不能藏起來自己當作採用了
- 衝突類的問題不附預設答案，一定要對方明確裁定
- 不要為了讓清單看起來精簡，把本質不同的疑慮合併成一個問題
- 每個問題都要可以被單獨回答，不要一題裡塞兩件不相關的事
- 範圍外聲明段落不能省略

## 輸出格式

```markdown
## 待確認事項（依急迫程度排序）

1. **[問題]**
   背景：為什麼會有這個疑問，來源是什麼
   預設：若沒空回覆，我會照 [預設方案] 往下走
   （若為衝突，不附預設，改為）來源 A 說：... ；來源 B 說：...

## 範圍外（除非你特別提出）
- 項目 — 判斷依據
```

## 完成後

提醒使用者：「這些問題送出去之後，對方的回覆記得用 `ingest-doc` 重新消化一次，並註明是回覆哪一則問題」——這樣回覆才會正確地成為下一輪迴圈的新資訊，而不是又變成一份孤立、沒有上下文的紀錄。
